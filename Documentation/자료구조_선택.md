# ZZZ Unity Project — 자료구조 & 디자인 패턴 선택 철학 

> 이 프로젝트에서 "왜 이 자료구조/패턴을 골랐나"를 면접에서 설명할 수 있게 정리한 문서.
> - **Part A. 자료구조** — 핵심 메시지: **런타임 핫패스(매 프레임 전투 로직)는 무할당(GC-free)으로,
>   데이터 정의부는 직렬화·가독성 우선으로** — 용도에 따라 다르게 골랐다.
> - **Part B. 디자인 패턴** — 핵심 메시지: **분기/타이밍은 데이터(ScriptableObject)로, 변하는 부분은
>   다형성으로 격리, 결합은 인터페이스로 끊어** 같은 엔진을 플레이어·몬스터가 공유한다.

---

# Part A. 자료구조

---

## 0. 한 줄 요약 

"매 프레임 도는 코드에서는 힙 할당과 박싱을 피하는 자료구조(배열·struct·제네릭 컬렉션)를 쓰고,
에디터에서 편집하는 데이터 정의부는 직렬화와 가독성을 우선해 `List<T>` 위주로 갔습니다.
측정 없이 추측으로 최적화하지 않되, GC를 만드는 게 뻔한 패턴(매 프레임 문자열·박싱)은
설계 단계에서 미리 배제했습니다."

---

## 1. enum을 Dictionary 키 대신 "배열 인덱스"로 — 박싱 + 힙 회피

**위치:** [InputBuffer.cs](../Assets/04.Scripts/Player/StateMachine/InputBuffer.cs)
```csharp
private readonly bool[] _held = new bool[Count];          // Count = enum 값 개수
public bool IsHeld(ComboInput input) => _held[(int)input];
public void SetHeld(ComboInput input, bool held) => _held[(int)input] = held;
```

**왜 이렇게?**
- 후보는 `Dictionary<ComboInput, bool>`였다. 하지만 구형 런타임에선 enum 키가 `object`로 **박싱**되고,
  엔트리마다 힙을 쓴다(+ 해시 계산 비용).
- `(int)input`은 박싱이 아니라 정수 변환 → **배열 O(1) 인덱싱**으로 박싱·힙·해시 비용을 전부 제거.
- 키 공간이 작고 연속적(enum)이라 배열이 Dictionary보다 모든 면에서 우월.

**면접 포인트:** "키가 enum처럼 작고 연속적이면 Dictionary보다 배열 인덱싱이 빠르고 무할당이다.
Dictionary는 키 공간이 크거나 희소할 때의 선택지다."

---

## 2. 사전 할당 버퍼 + NonAlloc — 매 탐색 할당 제거

**위치:** [EnemySensor.cs](../Assets/04.Scripts/Combat/EnemySensor.cs)
```csharp
private static readonly Collider[] s_hits = new Collider[16];
...
int count = Physics.OverlapSphereNonAlloc(transform.position, _radius, s_hits, _mask, ...);
```

**왜 이렇게?**
- `Physics.OverlapSphere`(비-NonAlloc)는 호출마다 `Collider[]`를 새로 할당 → 공격마다 GC.
- 고정 크기 버퍼를 `static`으로 한 번 잡고 재사용. 16개면 부채꼴 탐지엔 충분(예산 명시).

**면접 포인트:** "Unity의 `~NonAlloc` API + 사전 할당 버퍼는 빈번한 물리 쿼리의 대표적 무할당 패턴.
대신 버퍼 크기 상한을 정해야 하는 트레이드오프가 있다."

---

## 3. struct(값 타입)로 무할당 + 단위 테스트 가능

**위치:** [RootMotionTracker.cs](../Assets/04.Scripts/Movement/RootMotionTracker.cs)
```csharp
public struct RootMotionTracker { ... public Vector3 NextDelta(...) }
```

**왜 이렇게?**
- 루트모션 델타 계산은 매 프레임 도는 순수 계산 → `class`면 인스턴스가 힙에 산다.
  `struct`로 값 타입화해 힙 할당 0.
- Transform/씬 의존을 뺀 순수 함수라 **EditMode 단위 테스트** 가능
  ([RootMotionTrackerTests.cs](../Assets/Tests/EditMode/RootMotionTrackerTests.cs)).

**주의(면접에서 같이 말하면 좋음):** struct를 인터페이스 변수에 담으면 **박싱**된다.
그래서 인터페이스로 받지 않고 값 타입 그대로 사용. struct는 "작고, 불변에 가깝고, 자주 생성되는"
데이터에 적합하고, 크면 복사 비용이 역효과.

---

## 4. 제네릭 메서드로 struct를 박싱 없이 반환

**위치:** [PlayerController.cs](../Assets/04.Scripts/Player/PlayerController.cs)
```csharp
private void OnMove(InputValue value) => _moveInput = value.Get<Vector2>();
```
- `InputValue.Get<TValue>()`는 제네릭 → `Vector2`(struct)를 타입 그대로 반환, 박싱 없음.
- `object Get()` 방식이었으면 반환 시 박싱됐을 자리.

**면접 포인트:** "제네릭의 핵심 이점 중 하나가 value type을 박싱 없이 다루는 것."

---

## 5. HashSet — 멤버십 검사 전용

**위치:** [ConfigState.cs](../Assets/04.Scripts/Player/StateMachine/States/ConfigState.cs)
```csharp
private readonly HashSet<ClipLink> _latched = new HashSet<ClipLink>();
```

**왜 이렇게?**
- `OnEndIfMatched` 링크가 윈도우 안에서 한 번 충족되면 래치했다가 섹션 끝에 발동.
  "이미 래치됐나?"를 묻는 **중복 방지/멤버십 검사**가 목적 → Set이 의미상 정확하고 `Contains` O(1).
- 섹션 진입마다 `Clear()`로 재사용(섹션 스코프), 새로 할당하지 않음.

---

## 6. List<T> — 데이터 정의부의 기본 선택 (의도적 트레이드오프)

**위치:** [AnimationConfig.cs](../Assets/04.Scripts/Core/AnimationConfig.cs)
(`Clips` / `Links` / `GlobalLinks` / `Notifies` / `Modules`)

**왜 핫패스가 아닌데 List?**
- 이건 **에디터에서 편집하고 직렬화되는 데이터**라 우선순위가 다르다: Unity 인스펙터 직렬화 지원 +
  순서 보존 + 가독성. Dictionary는 Unity 기본 직렬화가 안 되고, 여기선 인덱스 접근/순회가 주 패턴.
- 순회는 전부 `for`/`foreach`인데 `List<T>`의 enumerator가 **struct**라 `foreach`도 무할당.
- `[SerializeReference] List<SectionModule>` — 다형성 모듈(i-frame/parry)을 한 리스트에 다형 저장.

**면접 포인트:** "핫패스냐 데이터 정의부냐에 따라 기준을 바꿨다. 전자는 무할당, 후자는 직렬화·가독성."

---

## 7. enum / [Flags] enum — 상태를 정수로 코드화

- `MoveMode`, `ComboInput`, `MoveDir`, `LinkTiming` 등 — 상태/조건을 enum으로. 비교가 정수 비교라
  무할당, switch 분기 명확, 직렬화 호환(값 추가는 끝에만).
- [PlayerStateFlags](../Assets/04.Scripts/Player/PlayerController.cs) `[Flags]` — 흩어진 bool들을
  비트마스크 한 값으로 모아 로그/HUD에 한 줄 표시.

---

## 8. 의도적으로 "안 쓴" 것 — Dictionary, 그리고 박싱이 있던 곳

- **Dictionary 미사용:** 섹션 검색 `AnimationConfig.IndexOfSection`은 `List` 선형 탐색.
  섹션 수가 적어(보통 한 자릿수) 선형이 더 단순·빠름. **다만 콤보가 크게 늘면
  `Dictionary<string,int>` 캐시가 후보** — "지금은 측정상 불필요, 커지면 전환" 이라고 답할 수 있게.
- **박싱이 실제 있던 곳 = 디버그 HUD뿐:** `Enum.GetValues` foreach + `$"{enumValue}"` 문자열 보간이
  enum을 박싱했음. 런타임이 아니라 디버그 코드라, `#if UNITY_EDITOR || DEVELOPMENT_BUILD`로
  릴리스 빌드에서 통째로 제외해 정리.

# Part B. 디자인 패턴

> 적용한 GoF/엔터프라이즈 패턴을 "왜 여기에 썼나"와 함께 정리. 패턴 이름을 외우는 게 아니라
> **어떤 문제를 풀려고 골랐는지**를 말할 수 있게 한다.

---

## P1. 데이터 주도 설계 (Data-Driven Design) — ScriptableObject 트랙

**위치:** [AnimationConfig.cs](../Assets/04.Scripts/Core/AnimationConfig.cs) · 자세히는 [AnimationArchitecture.md](AnimationArchitecture.md)

콤보·피격·회피·대시 연출을 코드가 아니라 **`AnimationConfig` 에셋(전이 트랙)** 으로 정의한다.
"언리얼 몽타주 스타일": 클립(섹션) + Link(전이) + Notify(이벤트) + Module(기능)을 에디터에서 편집한다.

- **왜?** 연출 변경마다 코드를 고치고 빌드하면 반복이 느리다. 분기/타이밍을 데이터로 빼면
  기획이 에셋만 만져서 콤보를 늘리고, 코드는 "데이터를 해석하는 엔진"으로 고정된다.
- **면접 포인트:** "행동을 코드가 아니라 데이터로 표현해 변경 비용을 빌드 사이클 밖으로 뺐다.
  Animator 파라미터/Transition도 안 쓰고 분기·타이밍을 전부 데이터로 모았다(단일 진실 공급원)."

---

## P2. Strategy + 다형성 직렬화 — 전이 조건(LinkCondition)·섹션 기능(SectionModule)

**위치:** [LinkCondition.cs](../Assets/04.Scripts/Core/LinkCondition.cs) ·
[Modules/](../Assets/04.Scripts/Player/StateMachine/Modules/)

"무엇이 충족인지"(조건)와 "무슨 기능인지"(모듈)를 `[SerializeReference]` **다형성**으로 분리했다.

```
LinkCondition (추상)              SectionModule (추상)
├── InputCondition                └── WindowModule (추상, 구간 판정 공유)
└── AlwaysCondition                   ├── IFrameModule  (무적)
                                       └── ParryModule   (쳐냄)
```

- **왜?** 새 조건(거리/체력/AI 결정)이나 새 기능(i-frame·parry)을 추가할 때 `ConfigState`·에디터
  본체를 안 건드리고 **클래스 1개만 상속**하면 된다(OCP — 확장엔 열려, 수정엔 닫혀).
- **과거→현재:** 조건을 `ClipLink`의 인라인 `Attack`/`Direction`/`RequireHeld` 필드로 들고 있었으나,
  다형성 `Condition`으로 이전·제거 완료(이 문서 P2가 [AnimationArchitecture.md](AnimationArchitecture.md)의
  마이그레이션과 같은 사건).
- **면접 포인트:** "알고리즘(조건 평가/기능 실행)을 인터페이스 뒤로 캡슐화한 Strategy. Unity에선
  `[SerializeReference]`로 다형성을 직렬화해 인스펙터에서 전략을 꽂는다. 단점은 타입 리네임 시
  직렬화가 깨질 수 있다는 것."

---

## P3. Template Method — WindowModule

**위치:** [WindowModule.cs](../Assets/04.Scripts/Player/StateMachine/Modules/WindowModule.cs)

"[Start, End] 구간 동안 무언가를 켠다"는 골격(루프 wrap 처리 포함)을 베이스(`InWindow`)가 한 번 정의하고,
**"무엇을 켜느냐"만 자식**(`IFrameModule`=`Invulnerable`, `ParryModule`=`ParryActive`)이 채운다.

- **왜?** i-frame과 parry가 구간 판정 로직은 똑같고 켜는 플래그만 다르다 → 공통 골격을 베이스로
  올려 중복 제거. i-frame('무시')과 parry('응수')가 대칭이라 읽기도 쉽다.
- **면접 포인트:** "불변 골격은 베이스, 가변 단계만 서브클래스 — 전형적 Template Method. Strategy(P2)와
  결합해 '구간 판정은 템플릿, 효과는 전략'으로 겹쳐 썼다."

## P4. Facade — PlayerStateMachine · AnimatorBridge

**위치:** [PlayerStateMachine.cs](../Assets/04.Scripts/Player/StateMachine/PlayerStateMachine.cs) ·
[AnimatorBridge.cs](../Assets/04.Scripts/Player/StateMachine/AnimatorBridge.cs)

- **`AnimatorBridge`** — Unity `Animator` 접근의 **유일 창구**. `Play(클립명)`=CrossFade, additive 흔들림을
  뒤에 숨긴다. 호출부는 `Animator` API를 직접 몰라도 된다.
- **`PlayerStateMachine`** — 협력 객체(InputBuffer/트리거들/ConfigRegistry/EnemySensor)를 조립하고
  무적·패링·입력 상태를 **facade 메서드로 노출**하는 얇은 코디네이터.
- **면접 포인트:** "복잡한 하위 시스템(Animator, 다수 트리거)을 단순한 상위 인터페이스 뒤로 감춰
  결합을 한 곳으로 모았다. 덕분에 Animator 접근 방식을 바꿔도 Bridge 안만 고치면 된다."

## P5. 인터페이스 분리 + DI — 플레이어·몬스터가 같은 엔진 공유

**위치:** [ConfigDriving.cs](../Assets/04.Scripts/Core/ConfigDriving.cs) · [Monster/](../Assets/04.Scripts/Monster/)

`ConfigState`(공유 러너)가 구상 타입(`PlayerController`/`AnimatorBridge`)에 직접 의존하지 않고,
작은 인터페이스(`IConfigMover`/`IAnimatorBridge`/`IConfigSignals` + `ILinkConditionContext`)에만
의존한다. 생성자로 구현체를 **주입**받는다(`new ConfigState(ctx, signals, condCtx, homeConfig)`).
이때 `ctx`는 위 표면들을 묶은 **구상 클래스 `ConfigContext`**다(번들 자체는 다형성이 필요 없어 인터페이스로 두지 않음).

```
                ┌── ConfigContext(구상 묶음) + PlayerConditionContext   (플레이어가 채워 주입)
ConfigState ────┤
 (추상에 의존)   └── ConfigContext(구상 묶음) + MonsterConditionContext  (몬스터가 채워 주입)
```

- **왜?** 피격·복귀 흐름이 플레이어·몬스터가 동일 → 상태머신을 새로 짜지 않고 **같은 엔진 재사용**.
  그러려면 엔진이 플레이어 구상 타입에 묶이면 안 되므로 의존을 인터페이스로 추출(DIP).
- **인터페이스 분리(ISP):** 입력 없는 몬스터는 `IInputMonitor`를 구현하지 않는다 → 라이브 모니터가
  입력 행을 자동 생략. "안 쓰는 멤버를 억지로 구현"하지 않도록 인터페이스를 잘게 쪼갰다.
- **면접 포인트:** "구상이 아니라 추상에 의존(DIP) + 인터페이스를 역할별로 분리(ISP)해서, 입력이
  있는 플레이어와 없는 몬스터가 동일 엔진을 서로 다른 컨텍스트만 주입해 구동한다."

---

## P6. 파라미터 객체 — 컴포넌트가 엔진 인터페이스를 구현, ConfigContext로 묶어 주입

**위치:** `PlayerController`/`MonsterController`(`IConfigMover`) · `AnimatorBridge`(`IAnimatorBridge`) · 묶음은 `ConfigContext`(구상)

씬의 구체 컴포넌트가 **직접 엔진 인터페이스를 구현**(`PlayerController : IConfigMover` 등)하고,
그 참조들을 `ConfigContext`라는 **구상 파라미터 객체**에 담아 `ConfigState`에 한 번에 넘긴다.

- **왜?** 엔진(P5)이 요구하는 추상(`IConfigMover`/`IAnimatorBridge`)은 컴포넌트가 직접 만족시키고,
  '묶음'은 캐릭터마다 바꿔치기할 일이 없어 인터페이스가 아니라 구상 클래스로 둔다 → 불필요한 간접층 제거.
  (이전엔 `Context`가 `IConfigContext`를 구현하는 어댑터였으나, 인터페이스-안-인터페이스가 혼란스러워 구상 `ConfigContext`로 단순화.)
- **면접 포인트:** "엔진은 인터페이스(DIP)에만 의존하되, 그 인터페이스 구현은 컴포넌트가 직접 맡고,
  주입은 구상 파라미터 객체(`ConfigContext`)로 묶어 단순화했다. 새 캐릭터는 같은 인터페이스만 구현하면 엔진을 그대로 쓴다."

## P7. Registry — 섹션 이름으로 config 조회

**위치:** [ConfigRegistry.cs](../Assets/04.Scripts/Player/StateMachine/ConfigRegistry.cs)

이벤트로 진입하는 config(Hit/Evade 등)는 개별 참조 필드를 두지 않고, 리스트에 **드롭만** 하면
재생할 **섹션 이름으로 자동 검색**(`FindWithSection`)해 진입한다.

- **왜?** 새 회피/피격 모션을 추가할 때 코드(필드 추가/배선)를 안 건드리고 에셋만 늘리면 된다.
  이름 규약(`Evade_*`, `Hit_*`)이 키 역할.
- **면접 포인트:** "객체를 이름(키)으로 등록·조회하는 Registry. 컴파일타임 참조 대신 규약 기반 조회로
  데이터 추가만으로 확장되게 했다. 트레이드오프는 문자열 규약 의존(오타가 런타임 미스)."

## P8. Trigger = Command 스타일 push 진입 (외부/전역 이벤트)

**위치:** [Triggers/](../Assets/04.Scripts/Player/StateMachine/Triggers/)
(`HitTrigger`/`DodgeTrigger`/`ParryTrigger`/`Attack_Normal_EnhanceTrigger`)

링크(데이터) 평가로 못 가는 강제 진입(피격·회피·패링·강화공격 폴백)을 **트리거 객체**로 캡슐화했다.
각 트리거는 `[Serializable]` 객체라 자기 설정(섹션 이름·blend·거리 임계)을 직접 들고 인스펙터에 노출,
런타임 의존만 `Init()`으로 주입받는다.

- **왜?** "어떤 조건에서 어떤 섹션으로 강제 진입"을 머신 본체에서 떼어 독립 객체로 → 머신이 비대해지지
  않고, 트리거별로 테스트·설정이 분리된다.
- **면접 포인트:** "동작 요청을 객체로 캡슐화(Command 결)해, 평평하던 상태머신 필드를 역할 단위로
  정리했다. push(강제 진입)와 데이터 링크(pull) 두 진입 경로를 명확히 나눴다."

## P9. Observer / 느슨한 결합 — 이벤트 & SendMessage

**위치:** [HitTarget.cs](../Assets/04.Scripts/Combat/HitTarget.cs) `OnDamaged` ·
`Notify(EventName)` → `SendMessage`

- **`HitTarget.OnDamaged`** 이벤트를 `MonsterStateMachine`이 구독 → 피격 시 Hit config 인터럽트.
- **`Notify(EventName="OnHitShake")`** 는 config가 "여기서 흔들림" 신호만 보내고, 실제 레이어/weight
  제어는 `AnimatorBridge`가 `SendMessage`로 느슨하게 받는다 → 흔들림 타이밍을 코드 수정 없이 에셋에서 조절.
- **면접 포인트:** "발신자가 수신자를 직접 모르게(Observer) 결합을 끊어, 데이터(Notify)와 코드(흔들림
  구현)를 분리했다. SendMessage는 편하지만 타입 안전성이 약한 트레이드오프가 있다."
- **→ 교체 예정:** SendMessage(리플렉션)를 **캐릭터별 강타입 이벤트 릴레이**(`event Action<string>`, 인스턴스 스코프)로 대체 예정 — Observer 결합은 유지하되 타입 안전성 확보 ([TODO.md](TODO.md))

## P10. 의도적으로 "안 쓴" 패턴 — 고전 State 패턴

> 패턴을 **안 쓴 결정**도 설계다.

상태 전환(콤보·대시·회피·피격 복귀)을 보통의 GoF **State 패턴**(상태마다 클래스, 인스턴스 교체)으로
짜지 않았다. 대신 `ConfigState` **단 하나**가 **config를 갈아끼우는(SwitchConfig)** 방식으로 처리한다.

- **왜 안 썼나?** 상태마다 클래스를 만들면 새 연출(콤보 한 단)마다 클래스가 늘어난다. 여기선 상태 간
  차이가 "코드"가 아니라 "데이터(어떤 클립/전이)"라, 상태=데이터(config), 엔진=1개로 두는 게
  클래스 폭발을 막고 P1(데이터 주도)과 맞아떨어진다.
- **면접 포인트:** "전형적 State 패턴 대신 데이터 교체형 단일 러너를 택했다. 상태의 차이가 행동
  코드가 아니라 데이터일 때, 클래스 증식보다 데이터 주도 단일 엔진이 유지보수에 유리하다."

---

## 패턴 요약표

| 패턴 | 어디에 | 푼 문제 |
|------|--------|---------|
| 데이터 주도(P1) | `AnimationConfig` | 연출 변경을 빌드 사이클 밖으로 |
| Strategy + 다형성 직렬화(P2) | `LinkCondition`/`SectionModule` | 조건·기능 추가 시 엔진 불변(OCP) |
| Template Method(P3) | `WindowModule` | 구간 판정 골격 공유, 효과만 가변 |
| Facade(P4) | `AnimatorBridge`/`PlayerStateMachine` | Animator·트리거 복잡도 은닉 |
| 인터페이스 분리 + DI(P5) | `ConfigDriving` | 플레이어·몬스터 엔진 공유(DIP/ISP) |
| Adapter(P6) | `*Context` | 컴포넌트를 엔진 인터페이스로 변환 |
| Registry(P7) | `ConfigRegistry` | 이름 규약으로 config 조회, 데이터만 추가 |
| Command 결 트리거(P8) | `Triggers/` | 강제 진입을 객체로 캡슐화 |
| Observer/느슨한 결합(P9) | `OnDamaged`/`SendMessage` | 데이터↔코드 분리 |
| (안 씀) 고전 State(P10) | `ConfigState` | 클래스 폭발 회피 → 데이터 교체형 |

## 면접 예상 질문 & 답변 뼈대

**Q. 박싱을 줄이려고 한 부분?**
→ #1(enum→배열 인덱스로 Dictionary 박싱 회피), #4(`Get<Vector2>()` 제네릭으로 struct 박싱 회피),
#3(struct를 인터페이스에 안 담아 박싱 회피). 실제 박싱은 디버그 HUD에만 있었고 빌드에서 뺐다.

**Q. 왜 어디선 배열, 어디선 List, 어디선 HashSet?**
→ 용도. 키가 작고 연속(enum)=배열 / 직렬화·순서·가독성 필요=List / 멤버십 검사=HashSet.

**Q. 최적화를 어떻게 접근하나?**
→ 측정 우선(Profiler GC Alloc). 단, 매 프레임 문자열·박싱처럼 GC가 뻔한 패턴은 설계 때 미리 배제.
모바일 빌드를 타겟으로 잡아 최적화 기준을 명확히 했다([TODO.md](TODO.md) 참고).

**Q. 지금 구조의 한계/다음 단계는?**
→ 섹션 검색 선형 탐색(콤보 증가 시 Dictionary 캐시), Notify 이펙트 풀링 미적용(반복 스폰 GC),
Addressables로 VFX 메모리 로드/해제 — 모두 측정 후 적용 예정.

**Q. 어떤 디자인 패턴을 썼나? (한 줄씩)**
→ 데이터 주도(P1)로 연출을 에셋화, 변하는 조건·기능은 Strategy+다형성 직렬화(P2)로 격리,
구간 판정은 Template Method(P3)로 공유, Animator/트리거 복잡도는 Facade(P4)로 은닉,
플레이어·몬스터는 인터페이스 분리+DI(P5)와 Adapter(P6)로 같은 엔진을 공유, config 조회는 Registry(P7),
강제 진입은 Command 결 트리거(P8), 피격/흔들림은 Observer·SendMessage(P9)로 느슨하게 결합.

**Q. 왜 고전 State 패턴을 안 썼나?**
→ 상태 간 차이가 "행동 코드"가 아니라 "데이터(어떤 클립/전이)"라서. 상태마다 클래스를 만들면 콤보 한 단
추가마다 클래스가 늘어 폭발한다. 그래서 `ConfigState` 단일 러너가 config를 교체(SwitchConfig)하는
데이터 주도 방식을 택했다(P10). 차이가 코드였다면 State 패턴이 맞았을 것.

**Q. 새 조건/연출을 추가하면 어디를 고치나?**
→ 거의 안 고친다. 새 전이 조건=`LinkCondition` 상속 1개, 새 섹션 기능=`SectionModule` 상속 1개,
새 피격/회피 모션=config 에셋 추가 후 리스트에 드롭(이름 규약). `ConfigState`·에디터 본체는 불변(OCP).
