# 주요 설계 결정

이 문서는 코드만으로 드러나지 않는 선택과 제약을 기록한다. 세부 동작은 [애니메이션 아키텍처](AnimationArchitecture.md)와 [이펙트 아키텍처](EffectArchitecture.md)를 참고한다.

## 런타임과 에셋 데이터의 기준

매 프레임 실행되는 코드는 불필요한 할당을 피한다. 반면 에디터에서 만드는 데이터는 Unity 직렬화와 편집 편의성을 우선한다.

| 영역 | 기준 | 사용 예 |
|---|---|---|
| 입력과 물리 탐색 | 반복 할당 방지 | 배열, `HashSet`, `OverlapSphereNonAlloc` |
| 루트 모션 프리뷰 | Unity 오브젝트와 분리된 값 계산 | `RootMotionTracker` 구조체 |
| Config 데이터 | 직렬화와 순서 보존 | `List<T>`, `[SerializeReference]` |
| 확장 지점 | 실행 코드 수정 최소화 | `LinkCondition`, `SectionModule` |

무할당 여부를 문서만으로 가정하지 않는다. 성능에 영향을 주는 변경은 Profiler로 확인한다.

## 입력 상태는 배열로 저장

[InputBuffer.cs](../Assets/04.Scripts/Agent/InputBuffer.cs)는 `ComboInput`을 배열 인덱스로 사용한다.

```csharp
private readonly bool[] _held = new bool[Count];

public bool IsHeld(ComboInput input) => _held[(int)input];
```

입력 종류가 작고 연속적인 enum이므로 Dictionary보다 배열이 단순하다. enum 값을 추가하거나 순서를 바꿀 때는 배열 크기와 직렬화된 Config의 값을 함께 확인해야 한다.

## 물리 탐색 버퍼 재사용

[EnemySensor.cs](../Assets/04.Scripts/Combat/EnemySensor.cs)는 `Physics.OverlapSphereNonAlloc`과 고정 크기 Collider 배열을 사용한다. 반복 탐색에서 배열이 새로 생성되는 것을 막기 위한 선택이다.

버퍼가 가득 차면 일부 대상을 놓칠 수 있으므로 크기 변경은 실제 전투에서 동시에 탐색될 수 있는 Collider 수를 기준으로 한다.

## 루트 모션 프리뷰 계산 분리

[RootMotionTracker.cs](../Assets/04.Scripts/Movement/RootMotionTracker.cs)는 AnimationConfigTool이 `RootT` 곡선을 프리뷰할 때 사용한다. Transform이나 씬 상태를 직접 참조하지 않고 이전 프레임과 현재 프레임의 값으로 이동량을 계산하며, 결과는 [EditMode 테스트](../Assets/Tests/EditMode/RootMotionTrackerTests.cs)로 검증한다. 런타임은 이 구조체 대신 `Animator.deltaPosition`을 직접 사용한다.

구조체를 인터페이스나 `object`로 다루면 박싱될 수 있다. 현재처럼 값 타입을 직접 보관하는 사용 방식을 유지한다.

## Config 데이터는 List 사용

[AnimationConfig.cs](../Assets/04.Scripts/Core/AnimationConfig.cs)의 Section, Link, Notify, Module은 `List<T>`로 저장한다.

- Unity가 기본 직렬화를 지원한다.
- 에디터에 표시되는 순서가 재생·평가 순서와 같다.
- 항목 추가와 재정렬이 쉽다.
- Module과 Condition은 `[SerializeReference]`로 파생 타입을 저장할 수 있다.

검색 성능보다 편집과 직렬화가 중요한 데이터다. 목록 크기가 커져 실제 병목이 확인되기 전에는 별도 인덱스를 추가하지 않는다.

## LinkCondition과 SectionModule

전이 조건은 `LinkCondition`, 재생 구간의 기능은 `SectionModule`로 분리한다.

```text
LinkCondition
├── InputCondition
└── AlwaysCondition

SectionModule
├── FaceInputModule / StartBoostModule
├── BackMotionScaleModule
└── WindowModule
    ├── AdditionalMovementModule / RotationLockModule
    ├── TargetWarpModule / FaceTargetModule / SectionTurnModule
    ├── IFrameModule
    └── ParryModule
```

새 조건이나 구간 기능은 가능한 한 해당 추상 타입의 구현으로 추가한다. `CharacterActionRunner`에 타입별 분기를 계속 추가하면 에디터와 실행 코드가 함께 비대해지기 때문이다.

`TrackClip`은 클립 재생과 전이에 필요한 공통 데이터만 가진다. 이동·회전·타깃 보정처럼
선택적인 동작은 모듈로 조합하며, `CharacterActionRunner`는 섹션 진입 시 이동기 상태를 기본값으로
초기화한 뒤 모듈의 `OnEnter`/`Tick`만 실행한다.

`WindowModule.Start/End`는 normalizedTime으로 저장하지만 AnimationConfigTool에서는 프레임으로
표시한다. 펼친 모듈 라인의 양 끝 핸들을 드래그하면 클립 프레임에 스냅된 값으로 갱신된다.

`[SerializeReference]` 타입의 이름이나 네임스페이스를 변경하면 기존 에셋의 참조가 깨질 수 있다. 리네임에는 명시적인 마이그레이션이 필요하다.

## CharacterActionRunner를 하나만 사용하는 이유

걷기, 공격, 회피와 피격은 별도의 State 클래스가 아니라 서로 다른 `AnimationConfig`로 표현한다. `CharacterActionRunner`는 현재 Config를 실행하고 필요할 때 `SwitchConfig` 또는 `InterruptWith`로 교체한다.

이 구조에서는 행동을 추가할 때 클래스보다 에셋이 늘어난다. 대신 `CharacterActionRunner`가 많은 기능을 조율하므로 다음 경계를 지킨다.

- 입력과 외부 진입 판단은 Trigger 또는 Condition에 둔다.
- 일정 구간에만 필요한 기능은 Module에 둔다.
- Animator 접근은 `IAnimatorBridge`를 통한다.
- 이동은 `ICharacterMover`를 통한다.
- 플레이어 전용 정보는 `ILinkConditionContext` 구현에서 제공한다.

이 경계 덕분에 플레이어와 몬스터가 같은 `CharacterActionRunner`를 사용할 수 있다.

## Registry 사용 범위

`ConfigRegistry`는 Section 이름으로 Config를 찾는다. 외부 이벤트가 진입할 Config를 직접 참조하지 않아도 되는 대신 이름 중복과 오타를 컴파일 시점에 잡을 수 없다.

- Section 이름은 프로젝트 안에서 충돌하지 않게 관리한다.
- 이름을 변경하면 해당 이름으로 진입하는 Trigger와 에셋을 함께 수정한다.
- 조회 실패를 조용히 무시하지 말고 에디터나 로그에서 확인할 수 있게 한다.

## 이벤트 사용 기준

Notify는 데이터가 코드의 동작을 요청할 때 사용한다. 수신자가 명확한 직접 호출까지 모두 이벤트로 바꾸지는 않는다.

- 재생 시점이 Config 데이터에 속하면 Notify가 적합하다.
- 한 객체가 명확한 협력 객체를 호출하는 경우 직접 호출을 유지한다.
- 전역 static 이벤트는 수명과 구독 해제가 불분명해질 수 있으므로 피한다.

## 이펙트의 실행 단위와 풀 단위

이펙트는 `CompositeEffect` 단위로 실행하지만 풀은 프리팹 단위로 관리한다.

- 하나의 연출은 여러 프리팹과 각기 다른 지연 시간을 포함할 수 있다.
- 같은 프리팹은 여러 조합에서 재사용할 수 있다.
- 풀 용량은 프리팹의 `EffectPoolConfig`에 한 번만 정의한다.
- 캐릭터가 사용하는 프리팹은 Config에서 찾아 소유권을 등록한다.

이 구조의 자세한 수명과 반납 과정은 [이펙트 아키텍처](EffectArchitecture.md)에 설명한다.

## 변경할 때 확인할 것

- enum 순서 변경이 배열 인덱스나 직렬화 값에 영향을 주는가
- `[SerializeReference]` 타입 변경이 기존 에셋을 깨뜨리는가
- Config 필드 변경이 두 에디터 도구에 반영됐는가
- 루트 모션 변경이 EditMode 테스트를 통과하는가
- 풀링된 이펙트가 재사용될 때 이전 재생 값이 남지 않는가
- 최적화가 필요한 경우 실제 Profiler 결과가 있는가
